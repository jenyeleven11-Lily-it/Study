# AI 个人任务规划 Agent：项目框架草案

> 状态：讨论稿 v0.1，供需求评审。本文先定产品行为和范围，不指定大模型、框架或部署方案。

## 1. 项目目标

做一个可以持续收集个人任务、记住任务与用户习惯，并在用户需要时协助判断“接下来适合做什么”的个人规划 Agent。

用户可以把任务随时放进一个任务盒，不必先确定截止日期或安排到某一周。Agent 根据任务内容估算任务类型、粗略耗时、重要性和不确定性；制定当天建议时，再结合用户当天的上课安排、当天健身计划、可用时间和历史反馈给出排序与建议。

核心目标是减少“任务很多，不知道先做哪个”的决策负担，同时避免把计划排得不现实。Agent 提供建议，由用户确认；不擅自替用户承诺或更改日程。

## 2. 用户与使用场景

- 用户有许多想做或需要做的事，其中一些暂时没有截止日期。
- 健身时间不是固定的；Agent 需要在当天规划时询问用户今天是否健身、计划何时健身或大约练多久。
- 上课时间会影响当天的可用时间。框架允许记录常规课表，并在临时变动时更新；课表录入方式属于待确认项。
- 用户不一定要按周规划。规划范围应由用户选择或在对话中确定，例如“现在做什么”“安排今天”或“看一下接下来几天”。
- 用户希望先把框架和边界定好，模型接入方式后续再选。

## 3. 核心使用流程

### A. 收集任务

1. 用户用自然语言添加任务，例如：“想学一下 LangGraph”“这周找时间把简历改好”“有空研究下摄影”。
2. Agent 将内容整理成任务卡片，并尽可能提取：任务名称、类别、粗略耗时、重要性/紧急度线索、是否有截止日期、前置条件。
3. 没有日期的任务保持无日期；Agent 不得为了排序而虚构截止日。
4. 如果耗时或任务含义很不确定，Agent 可以追问一个关键问题，也允许用户跳过，之后再补充。
5. 用户确认后，任务进入任务盒并持久保存。

### B. 规划当天

1. 用户发起“帮我安排今天”或类似请求。
2. Agent 读取当天已有信息：常规课表、用户记录的其他固定安排、未完成任务和历史偏好。
3. Agent 询问当天变化的信息，尤其是：
   - 今天是否健身？如果健身，计划大约何时、练多久？
   - 今天的上课安排是否与常规课表不同？
   - 今天还有没有其他必须留出的时间？
4. Agent 汇总可用时间；信息不足时明确说明假设，必要时继续询问，不把猜测伪装成确定安排。
5. Agent 给出适量任务建议，包括建议顺序、粗略耗时、安排理由和未安排任务的原因。
6. 用户可以接受、调整、跳过，或要求换一个排序。确认后的计划和反馈写入记忆。

### C. 临时重排

如果课程变化、健身计划变化或任务耗时超出预期，用户可以告知 Agent。Agent 重新评估当天剩余时间与任务，提出调整建议；经用户确认后再保存新计划。

## 4. 任务与记忆

记忆至少分成两类，避免把所有东西都塞进一段自由文本：

### 结构化任务记录

每条任务可包含：

- 任务 ID、标题、用户原始描述
- 状态：收集箱 / 待办 / 进行中 / 已完成 / 暂缓 / 已删除
- 类别与重要性线索
- AI 估算耗时及置信程度；用户修正后的耗时
- 可选截止日期、可选前置任务
- 创建时间、最近修改时间、完成时间
- 用户对建议的接受、修改或跳过记录

截止日期、重要性和耗时估计都允许为空；Agent 应区分用户明确提供的信息与 AI 推断。

### 用户规划偏好与历史

- 用户常见的可用时间、任务偏好和用户明确要求记住的规则
- 常规课表及临时例外（具体形式待确认）
- 任务类型的历史实际耗时，用于改善后续估算
- 用户接受、修改或拒绝建议的模式
- 每日健身计划作为当天信息记录；健身时间不作为固定日程推断

用户应能查看、修改和删除记忆；不确定是否长期有效的信息应先询问或设置有效范围。

## 5. 推荐逻辑原则

- **先满足硬约束：** 上课、用户明确的固定安排、明确截止时间。
- **再处理软偏好：** 任务重要性、预计耗时、精力要求、用户偏好、任务多样性。
- **估时要透明：** 给出粗略区间或标注低置信度；不能把估时当成事实。
- **适量推荐：** 计划应留出缓冲，不把每段空闲都塞满；具体缓冲规则由实际使用反馈调整。
- **解释推荐：** 说明推荐原因、耗时估计和关键假设，允许用户快速纠正。
- **尊重自主性：** 不自动删除、延期、添加截止日或更改课程/健身安排。
- **可修正、可学习：** 用户报告实际耗时或调整结果后，更新对应任务和偏好记忆。

## 6. 它算不算 Agent？

**按这个框架，它可以算一个有边界的交互式任务规划 Agent。** 它不只是一次性回答问题，因为它会持续接收目标、读取任务记忆、在缺少当天信息时追问、结合约束生成计划，并根据用户的确认或反馈更新状态。

建议第一版定位为“建议型 Agent”，而非自主执行 Agent：

- 会做：解析任务、询问上下文、读取记忆、估时与排序、生成计划建议、保存用户确认后的结果。
- 不会做：未经确认自动改课表、替用户创建外部日历事件、擅自延期任务或自动替用户执行现实操作。
- 不需要多 Agent：一个 Agent 配合任务存储和明确的规划规则，足以做出第一版。

大模型适合处理自然语言理解、补充问题和解释理由；硬时间约束、冲突检查和持久化应由明确的程序规则负责。这样能降低模型编造时间或忽略安排的风险。

## 7. 第一版范围（建议）

### 包含

- 自然语言添加、编辑、完成、暂缓任务
- 任务盒持久化；任务没有截止日期也能保存
- 常规课表记录与当天例外（若用户确认需要）
- 每次当天规划时询问当天健身计划
- 结合可用时间推荐当天优先任务，并解释理由
- 记录实际耗时和用户对建议的反馈
- 查看、修改和删除已保存的任务及偏好

### 暂不包含

- 自动接入微信、手机通知、第三方日历或定位
- 自动替用户执行任务或未经确认修改计划
- 复杂的多周甘特图、团队协作或多 Agent 编排
- 医疗、训练处方或健身负荷诊断
- 在尚未验证规划逻辑前追求复杂 UI 或大量功能

## 8. 如何判断第一版是否有用

先由用户本人连续试用一段时间，记录基线和使用结果，不预设成功数字：

- 从打开任务盒到选出下一项任务花费的时间
- AI 估时与实际耗时的差距
- 推荐被接受、调整或跳过的比例及原因
- 计划中任务完成情况，以及是否因安排过满而频繁重排
- 课程或健身临时变化后，调整计划是否省事

这些真实记录可以支撑后续 STARL 简历描述；项目完成前不填写虚构的提升幅度。

## 9. 待确认问题

1. **课表如何提供？** 录入每周重复课表，还是每天规划时由用户告知当天课程？也可以先录重复课表，再允许当天修正。
2. **“记忆”具体希望记住什么？** 是否包括已完成任务和实际耗时、长期偏好、历史计划？哪些信息需要自动过期？
3. **时间建议希望多精确？** 只排任务优先级和大致时长，还是需要给出具体时间段？
4. **任务是否要定期回顾？** 例如长期未处理的无日期任务，Agent 是否应主动提醒用户确认、暂缓或删除？
5. **健身计划需要记录到什么程度？** 只记录“今天去健身、大约多久”，还是也记录训练内容？

---

## 当前产品定义（一句话）

一个记得住个人任务和规划反馈、会主动询问当天课程与健身安排，并在用户选择的时间范围内给出可解释、可修改任务建议的个人规划 Agent。
